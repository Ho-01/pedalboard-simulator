# 개발 및 리뷰 절차

## 한 기능을 완성하는 순서

1. **plan**: 문제, 범위, 동작, 설계, 작업 순서, 완료 조건을 작성한다. 각 요구사항에 ID를 붙인다.
2. **사용자 검토**: 실제 문서 링크를 제공한다. 수정 의견을 반영한 다음 승인 발언·일시·범위를 plan에 기록한다.
3. **개발**: 승인한 범위만 작업 branch에서 구현한다. 코드 차이를 리뷰하기 쉽게 커밋한다.
4. **검증**: 빌드, 해당 동작, 화면, 오디오, 필요한 통합 검증을 확인한다. 미수행 항목은 구분한다.
5. **report**: 계획과의 차이, 이유, 검증 결과, 잔여 작업을 기록한다.
6. **코드 리뷰 및 반영**: 사용자가 report와 변경 파일을 확인할 수 있게 제공한다. GitHub 반영과 운영 배포는 각각 결과를 남긴다.

계획을 승인했다는 뜻은 해당 범위의 개발을 허용했다는 뜻이다. 운영 배포 승인 여부도 plan에서 명시한다. 승인 후 같은 작업에 반복해서 확인을 요청하지 않는다.

## 파일 이름

- plan: `docs/01-plan/26-10-08.bd2-mvp.plan.md`
- 대응 report: `docs/02-report/26-10-08.bd2-mvp.report.md`
- 날짜는 plan 작성일이다. report에는 실제 구현 완료일을 별도로 적는다.
- ADR: `docs/03-adr/0001.plan-review-report-workflow.md`처럼 번호를 순서대로 부여한다.

## Git을 처음 사용할 때

| 용어 | 이 프로젝트에서 하는 일 |
| --- | --- |
| repository | 코드와 변경 이력을 함께 저장하는 공간 |
| clone | GitHub 저장소를 작업 공간으로 가져오기 |
| branch | 이번 작업을 위한 별도 변경 흐름 |
| diff | 이전 코드와 바뀐 코드를 비교하기 |
| commit | 변경 내용을 한 단위로 기록하기 |
| push | 기록한 commit을 GitHub로 올리기 |
| PR | 변경 파일을 함께 보고 리뷰하기 위한 화면 |
| deploy | 특정 commit을 빌드해서 실제 서버에 반영하기 |

처음에는 `main`과 작업 branch만 사용한다. `develop` 등 여러 상시 branch는 만들지 않는다. 예: `feat/repository-and-deployment`, `feat/bd2-mvp`.

빈 저장소의 첫 commit에는 문서만 넣어 `main`의 기준을 만든다. 그 후에는 문서 plan을 먼저 공유하고, 승인 뒤 작업 branch에서 코드 diff를 검토한다. PR을 만들 수 있으면 활용하되 PR 생성 자체를 사용자에게 알림·메시지를 보내는 작업으로 확대하지 않는다.

## report 작성 기준

**일치**에는 `BASE-01, BASE-02`처럼 ID만 쓴다. plan에 이미 있는 구현 설명을 반복하지 않는다.

**차이·추가**에는 관련 ID, 계획 내용, 실제 구현, 변경 이유와 영향을 적는다. 차이가 없으면 `없음`이라고 쓴다.

**잔여 작업**에는 통합 검증, FE 의존 작업, 사용자 청취·브라우저 확인, 후속 plan을 적는다. 검증하지 않았으면 일치 항목에 넣더라도 완료 상태로 표시하지 않고 잔여 작업에도 남긴다.
