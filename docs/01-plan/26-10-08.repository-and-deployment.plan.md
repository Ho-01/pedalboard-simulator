## 1. 목표와 지금 확인한 사실

GitHub에서 변경 이력을 관리하고, 기존 GCP 서버에 특정 commit을 배포할 수 있는 가장 작은 구조를 만든다. 이 단계에서는 페달 기능을 구현하지 않는다.

2026-10-08 최초 조회 시 공개 저장소이며 commit이 없었다. 이후 문서 전용 commit을 작업 공간과 GCP checkout에 기록했다. 같은 날 사용자 리뷰 시점에는 GitHub 연결 계정 `Ho-01`과 이 저장소의 push 권한을 확인했다. GitHub API 쓰기 권한과 CLI push 인증은 별개이며, 실제 업로드한 commit을 확인하기 전에는 push 완료로 기록하지 않는다.

기존 GCP Nginx에 blog, greatkingdom, portfolio, familiar 등의 별도 host가 있다. 새 사이트는 별도 server block과 디렉토리를 사용한다. 서버 Node.js는 `v22.22.1`로 확인했다.

## 3. 가장 작은 구조

| 위치 | 역할 |
| --- | --- |
| `src/` | Workspace 화면과 이후 회로 데이터·브라우저 시뮬레이션 코드 |
| `public/` | 사진·오디오 등 정적 자원 |
| `docs/` | plan, report, ADR, 구조 및 운영 설명 |
| `scripts/` | 빌드 결과 배포·복구를 위한 작은 스크립트 |
| `deploy/nginx/` | 이 사이트의 Nginx 설정 예시 |

Node.js는 개발·빌드에 사용하고, 운영에서 앱용 Node 서버는 띄우지 않는다. 운영 Nginx가 `dist` 빌드 결과를 제공한다. DB·로그인·Docker·MCP는 이번 단계에 필요하지 않다. 이후 ngspice/WASM도 정적 자원으로 제공한다. native 참조 solver와 WASM 컴파일은 개발·검증 과정이며 운영 VM에 항상 떠 있는 계산 서버를 추가하는 뜻은 아니다.

배포 초안:

- 소스 checkout: `/home/ho/pedalboard-simulator`
- 빌드 release: `/var/www/pedalboard-simulator/releases/<commit-sha>/`
- 현재 서비스: `/var/www/pedalboard-simulator/current` → 해당 release
- Nginx: 이 사이트만의 server block에서 `current`를 정적 root로 사용

이미 있는 경로를 덮어쓰기 전에 실제 소유자와 내용부터 확인한다. 새 설정은 `nginx -t` 성공 후 reload한다. 정적 사이트이므로 앱 API 포트는 추가하지 않는다.

## 4. Git과 배포 순서

1. 이 plan의 사용자 승인을 기록한다.
2. 작업 branch에서 최소 앱을 만들고 로컬 검증을 수행한다. 승인 범위 내에서 Node 22 호환 버전을 선택해 lockfile로 고정한다.
3. GitHub 쓰기 연결을 확인하고 문서와 코드를 push한다. 로그인·토큰 발급은 사용자의 계정 인증 흐름을 사용한다.
4. 코드 리뷰가 가능하도록 변경 파일 및 commit을 제시한다. 검증된 배포 대상 SHA를 기록한다.
5. 그 SHA를 서버에서 checkout하고 빌드한다. 서버 공개 저장소 읽기는 HTTPS를 사용해 쓰기 권한을 요구하지 않는다.
6. 새 release에서 파일·버전 정보·로컬 응답을 검사한 다음 `current`를 전환한다. 첫 배포 실패 시 새 사이트만 비활성화한다.
7. 신규 HTTPS 주소, JS/CSS 자원, 버전 정보와 기존 서비스 응답을 확인하고 report를 쓴다.

처음에는 위 과정을 **수동으로 실행하는 배포**로 시작한다. push 자동 배포나 GitHub Actions는 별도 후속 plan으로 다룬다. Git commit과 서버 배포를 구분해서 배운다.

## 5. 검증 및 잔여 작업 처리

- 로컬 설치·타입 검사·빌드·확인 페이지를 실제 실행한다.
- 서버의 여유 디스크·메모리를 확인하고 순차 빌드한다. 메모리 부족이 있으면 build 산출물만 전달하는 방식으로 전환할 수 있으며 report에 차이를 기록한다.
- 배포 실패 시 새 release 활성화를 중단하고 이전 release를 유지한다.
- 성공한 정적 배포의 전환과 복구를 검증한다. 초기 release밖에 없으면 이전 SHA 복구 검증은 잔여 항목으로 남긴다.
- 최초 화면이 열렸다고 BASE-01의 GitHub push까지 완료로 처리하지 않는다. 인증 및 실제 원격 SHA 확인이 별도로 필요하다.
